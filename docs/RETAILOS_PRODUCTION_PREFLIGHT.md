# RetailOS production migration — preflight report

> **Operational documents:** the step-by-step procedure, the precondition checklist, backup instructions, environment checklist and stop conditions are in `docs/RETAILOS_PRODUCTION_RUNBOOK.md`. This report explains what the SQL does and records the dry-run results.

**Nothing in this document has been executed against the live Supabase project.** Prepared 2026-10-10 from the repository and from earlier read-only audits. Every statement that changes the live database needs separate, explicit approval.

**What local tests do and do not prove.** They run on an embedded PostgreSQL 17 loaded with `tests/db/prodlike.sql`, a *reconstruction* of the live project (from the read-only audit). They prove the SQL is internally correct, does not disturb the reconstructed Tirumala objects, and rolls back cleanly. They do **not** prove that the real project accepts it: the real project may differ from the reconstruction (other Tirumala objects, extensions, role settings, Supabase platform behaviour, the Data API).

### Review of the port (not a blind rename)
* Every function in the original design is `SECURITY DEFINER … set search_path = ''` or plain `set search_path = ''`, with schema-qualified names (checked by script for all 65 function definitions): nothing depends on `public` being searched.
* Cross-schema references are only `auth.uid()`, `auth.jwt()` and `auth.users` (the `profiles` foreign key and `retailos_private.ensure_profile`).
* The dynamic policy SQL in migration 0006 (`format('create policy … on public.%I … private.has_any_permission …')`) was inside strings; the generated file was inspected and targets `retailos.%I` / `retailos_private.`.
* Every policy (44 statements, plus those generated by the loop in 0006) is `to authenticated`; none for `anon`.
* No extensions, roles or `SET ROLE`; the only sequences are two identity columns (`audit_logs.id`, `inventory_movements.id`), written by SECURITY DEFINER functions.
* Statements that were **removed or redesigned**: global `alter default privileges … revoke execute on functions from public`; the three `in schema public` default-privilege statements (now `in schema retailos`); `revoke all on all tables in schema public …` (now an explicit list of the 13 tenancy tables); the trigger on `auth.users` (replaced by `ensure_profile`).
* **Behaviour change to know about:** `retailos.profiles.id` references `auth.users(id) ON DELETE RESTRICT`. A Supabase Auth user who has a RetailOS profile cannot be deleted until the RetailOS profile is removed. Tirumala's own `profiles` uses `ON DELETE CASCADE`, so an Auth-user deletion in the dashboard would fail for users who have been given RetailOS access. This is deliberate (audit trail), but it is an operational constraint to accept.

## 2. Preflight inspection of the production SQL

Statement inventory of the 14 migrations (comments stripped): 2 `create schema`, 35 `create table`, 65 `create function`, 41 `create trigger`, 44 `create policy`, 27 `create index`, 36 `alter table`, 33 `grant`, 21 `revoke`, 3 `alter default privileges`, 1 `drop policy`. `drop policy if exists role_discount_limits_write on retailos.role_discount_limits` replaces a policy of the *new* table (created in migration 0003). No `drop table`, `truncate`, or `delete` statements at migration level.

**Data written by the migrations:** only the permission catalogue and the global role defaults (`permissions`, `roles`, `role_permissions`). No tenant, no tax rate, no metal price (a sealed test enforces this). Everything else is created by running the app or the bootstrap script.

**The only statements that change something that exists today** (everything else creates new objects). These are the exact lines, copied from `supabase/retailos/migrations/20261010100001_foundation.sql`:

```sql
alter default privileges in schema retailos revoke all on tables from anon, authenticated;
alter default privileges in schema retailos revoke all on sequences from anon, authenticated;
alter default privileges in schema retailos revoke all on functions from anon, authenticated;
grant usage on schema retailos to authenticated, service_role;
```
Effect: (a) new tables created in `retailos` no longer receive the automatic `authenticated SELECT` that the schema's current default privilege adds; existing tables (the 10 live ones) are unchanged; (b) `service_role` gains `USAGE` on schema `retailos`. Both are reverted by `rollback.sql`.

Other effects to be aware of:
* Creating `retailos.profiles` with a foreign key to `auth.users` takes a brief `SHARE ROW EXCLUSIVE` lock on `auth.users` (one user today; milliseconds).
* `create schema if not exists retailos` is a no-op (the schema exists).
* Run as role `postgres` so ownership and default-privilege rules match the existing schema.
* Estimated run time: a few seconds in total.

## 3. Preconditions and backup requirements

1. Written approval of the exact files listed in section 7.
2. **Backup.** Confirm the Supabase plan provides backups or PITR and record the restore point time. If the plan has none, take a manual schema-and-data export of `public`, `cms`, `auth_custom`, `retailos` (`pg_dump` over the direct connection) *before* starting. Store it outside the repository. Do not rely on `rollback.sql` for Tirumala: it never touches Tirumala, so a backup is protection against the unexpected, not against this SQL.
3. Re-run the read-only catalog audit immediately before applying. **Stop** if: any `retailos_*` table has rows, `retailos` contains anything beyond the 10 live tables, new triggers exist on `auth.users`, or `public` has changed since the snapshot.
4. Run `verify/snapshot.sql` (read-only) and save the four hashes: `tirumala`, `live`, `auth_triggers`, `retailos_schema`.
5. Prefer a dry run on a Supabase branch or a restored copy if available. The local fixture is not a substitute.
6. Pick a quiet time; tell the Tirumala operators (no downtime is expected).
7. Decide how invited users are created before go-live: sign-ups are currently ON (see Tirumala proposal T0).

## 5. Rollback and its limits

`supabase/retailos/rollback.sql` (tested: after applying and rolling back on the fixture, the `public` schema, the 10 live tables, the `auth.users` triggers and the `retailos` schema privileges hash identically to the start).
* Drops 22 functions and 35 tables by exact name, then `retailos_private` (our helpers only), and restores the schema `USAGE` and the default privilege.
* **Limits:** all data written into the new tables is lost (including the bootstrap rows and any real sales); Auth users and invitations are not undone; it cannot undo dashboard changes (exposing the schema, sign-up settings); if someone later builds on these tables, the drop is destructive for them. It never drops schema `retailos`, so it cannot affect the 10 live tables. After real sales exist, do **not** roll back — restore from backup or fix forward.

## 8. Dry run on a catalog-faithful local clone (2026-10-10)

**No Supabase branch exists** (branches API: empty list) and creating one would be a new, likely billable resource, so none was created. The practical alternative was a **local clone of the live schema**, extracted read-only (`scripts/clone-live-schema.mjs`, Management API read-only SQL endpoint, catalog metadata only, **no rows copied**) into the git-ignored `.local/live-clone/` and replayed into an isolated embedded PostgreSQL 17 (`DB_BASE=live-clone`, `npm run test:db:clone`).

**Environment used:** embedded PostgreSQL 17.x (user-mode process on this machine, UTF-8, `--locale=C`) with a Supabase-like shim (roles `anon`, `authenticated`, `service_role`; `auth.users`, `auth.uid()`, `auth.jwt()`), then the clone: 39 tables (Tirumala `public` 16, `cms` 12, `auth_custom` 1, the 10 `retailos_*`), 5 views, 19 functions, 58 policies, 19 triggers (including `trg_on_auth_user_created`), grants, default privileges. Then the 14 adapted migrations, in order, as written to disk. The only SQL executed was: the replay of the extracted schema, `supabase/retailos/migrations/*.sql`, the verification queries, the test fixtures, and `supabase/retailos/rollback.sql`. Nothing ran against the live project except read-only catalog `SELECT`s.

**Fidelity proof.** `tests/db/live-clone-fidelity.test.ts` (5 tests) shows the clone's four catalog hashes (`tirumala`, `live`, `auth_triggers`, `retailos_schema`, from `verify/snapshot.sql`) are **identical to the live project's**, and that table/view/function/policy counts match.

**Results.** `npm run test:db:clone`: **224/224** (migrations apply; snapshots unchanged; `post_checks.sql` returns zero rows; RLS, grants, helper functions, membership authorisation, checkout transaction, idempotency, concurrency; rollback restores the start state with the 10 live tables untouched). `npm run test:db` (hand-made fixture): 219 passed, 5 clone-only tests skipped.

**What the clone does NOT reproduce (differences from production):** table data (Tirumala has real rows, e.g. products, invoices; none were copied, so locks, row-dependent constraint validation and timing on real data are untested); Supabase platform internals (event triggers, `pg_graphql`, realtime, Vault, `pg_stat_statements`, `supabase_admin`-owned objects, PostgREST and its schema cache, the Data API exposure setting); `uuid-ossp` (stood in for by `gen_random_uuid()`); hosted PostgreSQL 17.6 vs the local 17.x build; real Supabase Auth behaviour; extensions' own catalog entries; roles beyond the names needed for ACLs. **A passing clone proves the SQL is correct against the live catalog's shape, not that production is safe.**

**New findings from the real schema**
1. **No backups exist on the live project** (backups API: 0 backups, PITR off). Take a manual export before any change; this is now a hard precondition.
2. Tirumala's `profiles.role` has `CHECK (role IN ('admin','cashier'))` and its trigger copies `raw_user_meta_data->>'role'`. A sign-up with any other metadata role **fails entirely** (the `auth.users` insert errors). RetailOS invites send only `full_name`, so they are unaffected and receive Tirumala's default role `admin` (Tirumala proposal T1/T5).
3. Tirumala's `products` has a required `sku` and other required columns; the isolation tests now fill another app's required columns generically (`insertFilled`), so they run on both bases.

## 9. First-scan-after-Start-day investigation
Reproduced in the browser pane, then root-caused: the automation tool's `type` action inserts text **without key events**, so when focus was on `<body>` (a click had missed the scan box after the Start-day panel vanished and the layout shifted) the text had nowhere to go. A real key press fires `keydown`, the page moves focus to the scan box and the character lands (verified with a real key press). Real scanners were therefore not affected. A genuine robustness gap remained: the focused *Start day* button unmounts with its panel, dropping focus to `<body>`. Fixed in `billing-workspace.tsx` (focus the scan box after the day starts). Regression tests (`billing-workspace.test.tsx`, 4): the focus test failed before the fix and passes after; wedge-scan on `<body>`, scan during an in-flight Start day, and a rejected Start day.
